# Limit the archive to Git content

The managed archive preserves Git history and a usable checkout of each repository's default branch. StarSync issues no Git LFS or submodule commands of its own. Clones do not recurse, so submodule contents never enter the archive. Git LFS objects are whatever an ordinary clone or fetch produces on the host: where Git LFS is installed and configured, objects for the checked-out commit are downloaded with it; where it is not, the archive keeps only the LFS pointer files. StarSync neither requires nor disables Git LFS and never backfills objects for history outside the checkout, so LFS content in the archive depends on the machine that produced it. Complete dependency preservation was rejected because it can introduce unbounded storage, additional credentials, and failures in repositories outside the user's starred collection. As a result, the archive is not a complete backup of content stored outside the repository's ordinary Git object database.

When Git LFS is installed and its smudge filter fails because an object is no longer served, StarSync retries the operation once with `GIT_LFS_SKIP_SMUDGE=1` so the repository is archived with pointer files rather than lost. The fallback applies to a single failed clone or refresh and is never configured into the checkout, so an archive on a machine with working Git LFS keeps downloading objects normally.

StarSync also excludes GitHub-hosted material outside the primary repository, including issues, pull-request discussion, release assets, wiki content, and workflow artifacts. Exporting those resources would turn the tool into a GitHub account backup system with separate data models, retention rules, and API limits.
